## 2. Sentinel and non-glucose values

- Added one shared physiological gate: finite and 20..600 mg/dL, with the equivalent limit
  applied after converting mmol/L to mg/dL.
- `DisplayValueResolver` applies the gate to the raw/secondary lane. This covers Wear current
  snapshots and complications that resolve their value through `CurrentDisplaySource`.
- Wear chart selection text, range fitting, primary-raw fallback, secondary curve, and raw

- sync2 drops implausible raw values before writing them into the watch's native history, so

## 3. Calibrated values over sync2

- Added `/sync2/cal` and a versioned payload containing:
  - served sensor identity;
  - monotonic calibration-sync revision (so out-of-order Wear messages cannot restore stale
    anchors);
  - active auto and raw anchors as canonical mg/dL triples
    `[sensorValue, userValue, timestamp]`;
  - `valuesPrecalibrated` and `hideInitialWhenCalibrated` scalar state.
- The phone sends calibration state before every sync2 serve (full backfill and tail). Every
  calibration/UI-model change also queues a calibration resend plus a full 24-hour sync2
  re-serve so stored watch history is refreshed.
- Wear registers `SyncedWearCalibrationProvider` with `CalibrationAccess`, mirroring the
  explicit `TrendAccess` provider registration. It exposes active anchors/revision to existing
  consumers, including mode-appropriate auto/raw chart calibration droplets.

### How calibration is applied and why it matches the phone

The phone applies calibration while encoding each sync2 triple:

1. Native lanes arrive as canonical mg/dL x10.
2. The value is converted to the phone's current display unit because `CalibrationManager`
   stores/evaluates its model in the current display unit.
3. The encoder calls the existing `CalibrationAccess.hasActiveCalibration` and
   `CalibrationAccess.getCalibratedValue(value, timestamp, mode, sensorId)` separately for auto
   and raw lanes. This reuses the phone's selected algorithm, weighting, past-history policy,
   sensor enablement, and managed-driver ownership guard; no calibration formula was recreated.
4. The result is converted back to canonical mg/dL x10 and sent through the existing stream.

The Wear provider sees the payload's explicit `valuesPrecalibrated` contract and returns the
stream value unchanged, preventing a second application. It converts canonical anchors to the
watch display unit only at the UI boundary. This is deliberately safer than duplicating the
phone's multi-algorithm calibration engine on Wear.

## 4. Handoff control and duplicate sensor rows

- Wear `SensorScreen` always shows the claim state honestly:
  - phone owns sensor;
  - waiting to connect;
  - watch is reading the sensor.
- While `REQUESTING` or `CONNECTED`, it shows **Return sensor to phone**. The action calls
  `WearSensorClaim.setDirectRequested(false)`; that method immediately publishes both claim
  status and netinfo.
- Claim-state revisions now refresh the Wear screen immediately.
- Phone WearOS config observes `WearSensorClaimStatus` revisions, refreshes node state, and uses
  the remote claim state as the routing-toggle source when available.
- Turning the phone toggle off immediately sends routing/netinfo plus `/bluetooth false` and
  resumes phone Bluetooth; it no longer waits for the separate Save action.
- Wear sensor rows are collapsed using `SensorIdentity.matches`. Persisted managed identities
  are ordered first, so a managed record wins over its native alias. No native stores or managed
  records are deleted.
- Added localized Wear handoff strings in every Wear `values-*` locale.
